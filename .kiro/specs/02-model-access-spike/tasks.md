# Implementation Plan: Model Access Spike

## Overview

GitHub issue: #2

This plan runs the lightweight, MCP-based model access spike (the 3-hour time-box still applies) from the design and produces one committed file, `docs/spikes/model-access.md`. The work follows the design's investigation flow: preflight and Base_Commit, inference profile listing and Destination_Regions, subscription state and Verified_Calls, a throwaway harness outside the workspace, latency Runs per Candidate, the reasoning-settings comparison with manual quality judgment for Demo_Questions 1 to 5, quotas, the residency statement, writing the Decision_Record, and final hygiene checks. Languages and tools are the AWS CLI, Python 3.12 (harness only), and Markdown.

Project testing policy (`.kiro/steering/tech.md`): no automated tests, no eval harnesses, no test or verification scripts. Every place a test task would appear is a manual verification step instead. Each one names the action to run by hand and the observable pass result. Record what was checked, and the result, as a sub-bullet under that task (the task notes).

Rules that apply to every task:

- The only committed file outside `.kiro/specs/02-model-access-spike/` is `docs/spikes/model-access.md` (Requirement 8.1). Add no file under `scripts/`, `src/`, `infra/`, `data/`, or `ui/` (Requirement 8.3). Do not edit `README.md`; the README change from conflict C6 is a follow-up listed in the record.
- The harness (`harness.py`, virtual environment, raw timings) lives only in a folder made with `mktemp -d` outside the workspace. It is never committed and is deleted in task 12.1 (Requirements 3.8, 8.3, 8.9).
- Replace every account-specific value with `<ACCOUNT_ID>` or another angle-bracket placeholder before copying output into the record. Never paste `aws sts get-caller-identity` output (Requirements 8.4, 8.5).
- Do not copy the wording of any Demo_Question into the record or the Representative_Prompt. Refer to them by number and link to `.kiro/steering/product.md` (Requirements 3.10, 8.6).
- Use only IDs returned by the us-west-2 listing. The expected IDs in the requirements are leads, not facts (Requirements 2.3, 7.2).
- Time-box: 3 hours. If a block overruns, drop C3 first, then reduce quality runs to one answer per cell. Any criterion still unmet at 3:00 goes into the unmet list and the open items (Requirements 7.7, 7.8).
- Keep a scratch notes file inside the harness folder, not in the workspace, to hold command output and numbers until they are copied into the record.
- Scope (lightweight, chosen by the user): this spike covers access and Verified_Calls, inference profile listing and Destination_Regions, quotas, residency, and the decision record. The local Strands harness, the 10-run latency measurements, and the reasoning-settings comparison with quality judgment (tasks 5 to 8) are deferred and optional. Their criteria (Requirement 3, Requirement 4, and the latency-based parts of 5.3) go to the record's unmet list and "Open items and follow-ups" (Requirement 7.8) with the reason "deferred by the user: shell AWS calls blocked by sandbox; local harness to be run by the user later".
- All AWS calls in this spike go through the AWS MCP server tool `aws-mcp` `run_script` (Python with `call_boto3(service_name, operation_name, region_name, params)`, `region_name="us-west-2"`), because shell `aws` calls are blocked by a sandbox rule on credential reads. Extract and redact account IDs inside the script; never return or write them. Where a task names an `aws` CLI command from the design, run the equivalent boto3 operation through `run_script` instead.
- The named-profile `export` lines from design Step A apply only to a command the user runs in their own terminal (for example the deferred harness). Quote the profile name because it contains colons.
- Candidate change (2026-11-20): Claude Sonnet 5.5 (US and global profiles) and Claude Haiku 5.5 are not available for this account (every `Converse` call in us-west-2 returned `AccessDeniedException` "<model> is not available for this account"; `agreementAvailability` stayed `NOT_AVAILABLE`; recorded in the old notes of tasks 3.1 and 3.2).
